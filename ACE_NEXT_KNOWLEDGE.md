Installed v68 (2026-11-20, roles v9) implements the approved software, ML, forward deployed, integration/systems, algorithm and data families under the same experience rules, reads an underscore in a title as a space and passes a technology programme title that names no other occupation. PhD, compiler/runtime/QA, seniority, internship/contract, hardware/security, mobile and specialist infrastructure exclusions remain; existing software/ML infrastructure exceptions stay. Reject open-ended 3+ and above, explicit no-sponsorship, ITAR and citizenship requirements. Silence is unknown, not rejection. Every change needs a version bump, tests, a corpus dry run (`backend/scripts/gate_dry_run.py`) and a stale-row backfill before live acceptance. The backfill CLI recomputes hashes, so jobs still stored under an older hash formula stay stale after it; finish with the stored-hash `refresh_stale_evaluations` (or fix the CLI) and require zero stale rows. Details: `docs/knowledge/01-gate-and-roles.md`.

**Coverage.** Each tab says in plain words what it is. The Scoreboard carries the daily test-list score and the counted-once groups; Sources carries the reading-schedule table. Test lists are never read to find jobs (REC-03). Adding by hand always answers on screen, keeps a lead whatever happens, and asks robots first; a board switched off earlier stays off. Since 2026-11-12 the scheduler adds a lead's board once it reads, is one employer's and hires US engineers (owner request); a board the catalog holds, on or off, is never touched. A missed test-list role is fixed only by reading the company's own board: such boards are added after the registration checks as `missed_role`, and the score counts their roles apart (`board_added`, `added_companies`). The score matches a role by the board its link names, whatever name ACE holds it under. New SmartRecruiters boards are not added while its API's robots rules refuse. No manual work (owner, 2026-11-23): the daily fix tries missed roles' boards, and leads come from the daily check, FreeHire weekly, YC names daily (never YC's pages), Hacker News every six hours, the owner's quarterly visa filing files and regional networks; the lead check reads each board before adding it. Needs you lists every missed role with its posting and what ACE did. Details: `docs/knowledge/03-coverage-and-discovery.md`, `05-web-ui.md`.

**Discovery.** One adapter per platform. Job identity is (source, source_account, external_id); numeric IDs are internal. Only a complete snapshot can close jobs; a partial, empty, refused or non-authoritative read never does (`close_missing=False`). Conditional HTTP, bounded jittered retries, refusal backoff up to six hours, restarts resume persisted schedules. Ten workers in fair turns (a board starts only when a worker is free, oldest due first, Workday at most 3 and Oracle at most 2 at once; `SCHEDULER_WORKERS`, `SCHEDULER_PLATFORM_LIMITS` set in the image override); every Workday request waits on one steady pace (start 6 a minute, halves on a refusal down to 1, rises a quarter after 20 answers in a row up to `SCHEDULER_WORKDAY_PACE_MAX`, 150, enough for every Workday board on its plan); three Workday refusals within five minutes with no answer pause all of Workday (10 minutes doubling to 2 hours); Workday boards with matching roles go first; every Workday request offers OpenSSL's standard cipher list under ACE's honest name and the first bot check (`cf-mitigated: challenge`) stops all Workday reads for a day, never retried (owner approval 2026-11-19); quick reads go by each career site's sitemap (robots.txt names it; newest 100 postings, a page read only for a new posting whose title could pass) and the daily full read asks the job API, which rests after a refusal (30 minutes doubling to six hours); sitemap and page requests keep their own pace; the scheduler's Workday pause holds every reader in the process (`scheduling/holds.py`); stored posting details are reused; every Greenhouse, Ashby, Lever and SmartRecruiters board every 15 minutes; an unchanged posting is not rewritten, its last-seen time refreshed at most hourly; maintenance every 30 minutes, the daily score first; the dark-board check never moves a Workday or Workable board (their silence is the platform's refusal). New boards go through `backend/scripts/register_network_boards.py`, a dry run by default: it reads each board once and adds it only if it reads, is not an agency or shared board, and has a US software or ML role. A board with a passing role polls every 15 minutes, others hourly. Workable refuses the VM with 429s. The employer's own posting is the apply link; the exceptions are RippleMatch and a zapply copy of a posting ACE cannot spell (zapply's own link, which forwards the owner's click; ACE never opens it). New boards are never added on a host whose stored robots verdict refuses ACE (feed-link sweep and dark-board check included), nor on an Oracle or Workday test-system host. Readers since Chat 8: Workable's public job file (hourly list copies, saved to disk before reading), SuccessFactors (job feed), BambooHR, Rippling and Paylocity (list, then promising postings), iCIMS (sitemap and JobPosting); Paycom and ADP are not read. Details: `docs/knowledge/02-sources-and-scheduler.md`, `03-coverage-and-discovery.md`.

**Applications.** Identity is `job:<id>` from applied marks plus `external:<id>` records; separate applications are never fuzzy-merged. Marked pages ignore gate and active filters so history never vanishes. No spreadsheet import UI. "Applied before" is read-time evidence and never copies a mark.

**Company logos.** `CompanyLogo` and `CompanyIdentity` on every structured company surface: 85 reviewed bundled assets with provenance, then the owner-only `/api/company-logo` route using only verified sources. Never guess a domain, borrow a parent's mark or fabricate a logo; missing evidence shows initials.

**Resume Studio.** Deterministic, no generative AI yet. Facts are separate from wording and only verified facts count. The ATS checker reports an "Estimated ace compatibility score", never an employer's score. Tailoring and export are not built.

**Authentication.** One owner, no registration. Argon2id, hashed sessions, CSRF on mutations, email codes when mail is configured. Google sign-in binds the owner's subject. ## Release procedure

Prepare and test first, bind the exact tested SHA and operation, and follow the latest owner authorization. If the agent's permission check refuses a production step, stop and offer the owner the exact command; never work around it. A release with a migration adds a real restore drill into a throwaway container with no network (about 4 minutes), a schema-only rehearsal including a downgrade, and runs `compose run --rm --no-deps migrate` before the services; the scripts that did this are in ignored `artifacts/requirements-chat-1-20261105/release/`, and section 13.5 of the requirements file explains them. For a schema-free release:

1. Inspect what is running: commits, images, container IDs, schema, private inventory.
2. Take a fresh private backup in `/opt/ace/private-backups/<name>-<UTC stamp>/` (directory 700, dump 600). Check gzip, archive catalog and full expansion. This is not a restore drill. No pruning.
3. Tag each prior image `oracle-<service>:before-<name>-<stamp>` and write a guarded rollback that replaces only that service.
4. Build the exact source with its SHA embedded, then activate only what changed: `docker compose --env-file .env -f deploy/oracle/compose.yaml up -d --no-build --no-deps --wait --wait-timeout 180 <service>`. Always pass `--env-file .env`. Never run `down`, remove volumes or recreate unrelated services. A migration or scheduler change needs its own approval.
5. Verify public `/healthz` and `X-Ace-Frontend-Commit`, served asset hashes, anonymous auth boundaries, installed read-only audits, protected row hashes (HMAC snapshots across 19 tables before and after), unrelated container IDs, private configuration hashes and inodes, schema and logs.
6. Record the outcome here in a few lines and the proof privately. Separate source and HTTP checks from signed-in browser checks.

Access: `ssh -i ~/.ssh/ace_oracle ubuntu@161.153.89.170`, checkout `/opt/ace`. Never print `.env` or expanded Compose configuration. The agent's permission check can refuse production reads until the owner approves in that chat.

Lessons: a scheduler has no `--wait`, because its health check first runs after five minutes, so wait for `ace_scheduler_ready` in its log. In SSH `bash -s`, give non-input `docker compose exec` calls `</dev/null` or they swallow the remaining script. With `pipefail`, `gzip -dc | pg_restore --list` can exit 141, so run `gzip -t` first and use process substitution. Start long VM builds with `nohup` and poll a log. Use umask 022 for checkouts and 077 for private files. Health alone once missed unreadable new assets, so check hashes through public HTTPS. Never overlap one operation's verification window with another operation's restart (Chat 4 lost two verify attempts that way), and record measured numbers before strict checks. A strict polling-settings check must accept the scheduler's own proven actions (logged or data-proven cadence promotions, moved-board repairs by dark_source_recovery). Release phases run on the server in their own session and survive the chat ending; a laptop watcher does not (Chat 4 lost two, and the owner got no report). After any interruption, read the server first with the release folder's `status.py`, and never relaunch a phase that has a log.
